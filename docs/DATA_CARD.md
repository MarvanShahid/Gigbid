# Data card

## What this data is

**A synthetic stand-in.** The instructor's starter kit (GigSim, three persona corpora, policy pack, ~1,500
historical jobs, the 200-job-per-persona dev set) was not available when this was built, so everything here
is generated by `scripts/build_standin_data.py` with a fixed seed (800). Every number in the README and report comes
from this stand-in and **will change** when the real kit is dropped in (`gigsim/`, `data/personas/`,
`evals/datasets/`). Results computed on the stand-in should not be compared with classmates' numbers.

| Clients | 160 | public history + hidden preferences (generic-opening dislike, budget tolerance, evidence, max words); 10% "bad" |

Job kinds: fit (45%), partial (15%), off-domain (20%), scam (10%), lowball (10%); ~8% carry an injected instruction;
6 duplicates per persona.

## How the gold labels are defined (and why that matters)

* **bid** = not a scam, ≥75% of requirements in the persona's domain, budget ≥ 8 h at the persona's floor, not a lowball,
  client not "bad". This is a rule of the generator, so a system that learns the same rule can score high: treat
  decision metrics as an upper bound.
* **scam** comes from five fixed pattern families (free sample work, off-platform chat, crypto payment, bank details,
  "buy our starter kit"). GigBid's rule list was written knowing these families, so **scam recall of 1.0 on this set is
  not evidence it would catch new scam wording**; the hidden test set will be the real measure.
* **relevant evidence** = every project whose skills (including code-only skills) intersect the job's requirements.
  Metrics are therefore project-level, and Recall@5 is computed against min(5, |gold|).
* **fair price band** = ±20% around a category- and complexity-based centre. Complexity is not visible in the post,
  which explains part of the "mispriced" failures.

## Simulated clients

Rule-based, not an LLM (the real GigSim uses one). A proposal gets a reply when its score
(requirement coverage by name × evidence preference − generic opening − over-budget − over-length + true fit + noise)
passes a threshold. So the reply rate rewards naming the client's requirements and staying specific. It
does not measure persuasion. Results on this simulator over-reward keyword coverage. See the report's discussion of
where better retrieval did not translate into replies.

## Privacy

All persons, clients and companies are invented. No real client data and no live-mode data are in the repo.
